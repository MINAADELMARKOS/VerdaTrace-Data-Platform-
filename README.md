# VerdaTrace Data Platform

VerdaTrace is a GCP-native, production-oriented reference platform for governed logistics, mobility, IoT, environmental, climate, and geospatial data. It preserves the repository's original Pub/Sub → Python worker → BigQuery/GCS architecture and adds independently testable layers for ingestion, cataloging, quality, analytics, suitability evaluation, normalized results, lineage, auditing, and visualization intelligence.

The public portal consumes a normalized result generated by the same Python pipeline used in tests; it is not a disconnected mock dashboard.

## What is implemented

| Capability | Implementation |
| --- | --- |
| Dataset registry | Versioned, typed YAML definitions discovered from `config/datasets/*.yaml`, with deterministic ordering, duplicate-ID rejection, source validation, and reusable registered execution. |
| Ingestion | Bounded CSV, JSON, JSONL/NDJSON, XML, GeoJSON, and streaming OSM `.osm.pbf` readers; Pub/Sub event streaming; safe path roots; allow-listed HTTPS JSON connector; GeoTIFF header probe and explicit raster-worker boundary. |
| Catalog | Evidence-based field semantics, dataset categories, confidence, sample evidence, geographic bounds, and temporal coverage. |
| Quality | Nulls, required fields, duplicates, datatypes, timestamps, WGS84 coordinates, suspected swapped axes, humidity, non-negative physical readings, configured domain constraints, gaps, staleness, IQR outliers, CRS consistency, GeoJSON geometry validity, and OSM classification checks. |
| Analysis | Descriptive statistics, temporal aggregation and trend change, grouped statistics, correlations, mobility distance/speed summaries, and bounding boxes. |
| Evaluation | Structured task suitability across completeness, validity, sample size, temporal axes, spatial readiness, and metric compatibility. |
| Results | Typed implementation-neutral results with metrics, dimensions, units, warnings, provenance, quality references, lineage, a nullable source/processing manifest, measured processing counters, bounded quarantine records, and optional source-backed executive KPIs. |
| Visualization | Deterministic line, scatter, histogram, bar, point, proportional-symbol, heatmap, route, line-map, geometry-distribution, temporal-spatial, polygon, choropleth, and raster recommendations with reasons and warnings. |
| Interactive portal | Dynamic catalog search and metadata filters, direct dataset links, safe empty/error states, optional KPI cards, dataset manifests, Leaflet point/route/bounds layers, zoom/pan, tooltips, layer controls, temporal filtering, map-bounds filtering, field selection, canvas trends, catalog evidence, lineage, quality, and governance. |
| Security | Role/permission matrix, secret redaction, path/URL validation, workload identity, Secret Manager retrieval, bucket/dataset/subscription scoped IAM, non-root containers, and public-access prevention on raw storage. |
| Governance | Owner, source, license, classification, sensitivity, retention, timestamps, transformation history, schema version, quality status, geographic/temporal coverage, and explicit unknown values. |
| Audit and lineage | Structured audit events and source → raw → catalog → quality → analysis → evaluation → optional KPI → visualization lineage without raw-row or secret logging. |
| Cohesive data pack | Streaming CSV/JSONL/XML ingestion, GeoJSON profiling, rule-driven quality validation, cross-domain Zone/Site/Vehicle/Sensor rollups, explainable suitability, executive KPIs, lineage edges, RBAC policy, and bounded browser previews from the supplied synthetic pack. |

## Representative data

The repository intentionally separates real data from fixtures:

- `data/samples/open_meteo_cairo_2024-01-01_2024-01-03.json` contains 72 real, attributed hourly observations retrieved from Open-Meteo. Data are CC BY 4.0 and the exact request URL, retrieval timestamp, schema, transformations, coverage, and limitations are embedded with the records.
- `tests/fixtures/synthetic_mobility_route.geojson` is clearly labeled synthetic logistics/mobility/sensor data for deterministic tests and the public UI.
- `tests/fixtures/synthetic_sensor_quality_cases.csv` and `broken_polygon.geojson` are deliberately invalid test fixtures.
- `config/datasets/osm_egypt_retrieval.yaml` is a disabled, source-backed OpenStreetMap Egypt PBF retrieval plan. The large binary is not committed; enable it only after a verified Geofabrik download and an approved `pyosmium` worker are available. See [docs/osm.md](docs/osm.md).
- `config/datasets/*.yaml` contains executable definitions for the included Cairo and refrigerated-route datasets. Large NYC TLC, Natural Earth, and Kaggle sensor sources remain retrieval-only candidates; their provenance, redistribution decisions, schemas, and limitations are recorded in the legacy `config/datasets.json` catalog until compatible source files/adapters are available.
- `data/cohesive_pack/` contains the supplied pack's README, manifest, schemas, catalog/rules, golden quality findings, lineage, visualization, and RBAC metadata. The generated raw files are not committed; use `--pack-root` to reproduce them. The public payload was built from the full supplied pack and contains bounded previews plus measured aggregates. See [docs/cohesive_data_pack.md](docs/cohesive_data_pack.md).

See [docs/datasets.md](docs/datasets.md) for the full source evaluation, including every candidate dataset in the request.

## Dataset onboarding

An executable dataset is one YAML file under `config/datasets/` using schema `verdatrace_dataset_config_v1`. The two existing definitions preserve Cairo Historical Weather and the Synthetic Refrigerated Shipment Route.

```yaml
schema_version: verdatrace_dataset_config_v1
id: example_dataset
name: Example dataset
domain: environmental
task: descriptive
required_fields: [event_id, event_timestamp]
source:
  path: data/samples/example.json
  format: json
  dataset_type: tabular
  fixture: false
  provider: not_provided
  retrieved_at: not_provided
  license: not_provided
  geographic_coverage: unknown
  temporal_coverage: unknown
quality: {}
governance:
  owner: not_provided
  sensitivity: not_provided
  retention_policy: not_provided
```

The registry accepts repository-relative existing files in CSV, JSON, NDJSON, GeoJSON, TIF/TIFF, and explicitly bounded raster placeholders (`COG`, `NetCDF`, or `Zarr`) form; the declared format must match the extension. A definition may set `enabled: false` for a documented retrieval-only source whose file or credentials are not yet available; disabled definitions are validated but never executed or published. Dataset type must be `tabular`, `vector`, `raster`, or `streaming`. Supported tasks are `auto`, `general`, `descriptive`, `time_series`, `sensor`, `climate`, `spatial`, `mobility`, and `correlation`. Unknown keys, invalid field lists/ranges, non-positive telemetry ages, unsupported values, path traversal, missing enabled sources, and duplicate IDs fail explicitly.

Source provenance, attribution, quality domain constraints, telemetry freshness, and governance may be supplied when known. Use `unknown` or `not_provided` when they are not known; do not estimate source facts, sizes, or business KPIs. See [docs/architecture.md](docs/architecture.md#executable-dataset-registry) for the execution and payload contracts.

## Quick start

Python 3.11 or newer is recommended.

```
python -m venv .venv
.venv\Scripts\activate
python -m pip install -r requirements-dev.txt
python -m pytest -q
```

Run the original compatible single-event transformation:

```
python data_pipeline.py --local-sample sample_events/nyc_taxi_trip.json
```

Refresh the real Open-Meteo sample and rebuild the portal payload:

```
python scripts/fetch_open_meteo.py
python scripts/build_demo.py
```

Build the cohesive synthetic pack extension (after extracting the supplied ZIP):

```
python scripts/build_demo.py --pack-root C:\path\to\verdatrace_data_pack --preview-limit 300
```

This appends all pack datasets to the same catalog and emits `platform` rollups
for Executive Overview, Cross-Domain Explorer, quality golden-target validation,
lineage, and governance/audit. Raw pack files remain outside Git.

`scripts/build_demo.py` discovers every validated definition in `config/datasets/`, delegates each one to `run_registered_dataset`, and writes one portal entry per definition. Its optional flags are `--project-root`, `--registry`, `--output`, `--actor`, and `--preview-limit` (the browser payload bound; full pipeline analytics still use the source snapshot); for example:

```
python scripts/build_demo.py --registry config/datasets --output frontend/data/platform_demo.json
```

Run the complete local pipeline over the registered real sample:

```
python scripts/run_multimodal_flow.py ^
  --input data/samples/open_meteo_cairo_2024-01-01_2024-01-03.json ^
  --allowed-root data ^
  --dataset-id open_meteo_cairo_historical ^
  --task climate ^
  --output data/intermediate/open_meteo_result.json
```

Open the interactive portal:

```
python -m http.server 8080 --directory frontend
```

Then visit `http://127.0.0.1:8080`.

## User workflow

1. Search the catalog by dataset name, ID, or domain, or use the generated domain and dataset-type filters.
2. Select any returned dataset. A static deep link such as `?dataset=open_meteo_cairo_historical` opens a known ID; an unknown ID falls back safely to the first available dataset.
3. Inspect the source/processing manifest, detected categories, semantic fields, evidence, confidence, temporal coverage, and spatial bounds.
4. Review the machine-readable quality status and issue details.
5. Inspect descriptive, temporal, mobility, and spatial analytical outputs.
6. Review task suitability and any remediation warnings.
7. Read visualization recommendations, fields, confidence, and deterministic reasons.
8. Explore supported embedded point/route layers, change the temporal window, filter to map bounds, and select the chart metric.
9. Trace the result to its source and inspect governance/audit metadata.
10. Use the Cohesive Operating View to select a zone and compare logistics, mobility, sensors, climate, GIS, quality, suitability, and recommendation evidence in one workspace.

## Ingestion

### Local files

`verdatrace.ingestion` supports CSV, JSON arrays/objects/envelopes, NDJSON, and GeoJSON FeatureCollections. Readers validate approved roots and stream CSV/NDJSON records. `iter_batches` prevents unnecessary all-at-once cloud writes.

GeoTIFF/TIFF is recognized and safely probed. CRS, band, transform, and tile processing are deliberately delegated to an optional rasterio/GDAL worker because the original repository has no raster stack. Unsupported or corrupt rasters fail explicitly.

### Telemetry and Kaggle

```
kaggle datasets download -d garystafford/environmental-sensor-data-132k -p data/raw --unzip
python scripts/kaggle_to_pubsub.py ^
  --project "$PROJECT_ID" ^
  --topic verdatrace-transaction-events ^
  --use-case environmental_sensor_telemetry ^
  --csv data/raw/iot_telemetry_data.csv ^
  --limit 100000
```

The Pub/Sub publisher waits for every publish result and attaches dataset/use-case attributes. Do not commit the 61.93 MB source file.

## GCP deployment

```
terraform init
terraform plan -var="project_id=$PROJECT_ID"
terraform apply -var="project_id=$PROJECT_ID"

docker build -t REGION-docker.pkg.dev/$PROJECT_ID/verdatrace-data-platform/worker:VERSION .
docker push REGION-docker.pkg.dev/$PROJECT_ID/verdatrace-data-platform/worker:VERSION
kubectl apply -f deployment.yaml
```

Create a Secret Manager version for `verdatrace-pseudonym-salt` out of band. No secret value is stored in Terraform, Kubernetes YAML, source code, or container images.

Runtime variables:

| Variable | Purpose | Default |
| --- | --- | --- |
| `GCP_PROJECT` | Project containing the scoped resources | required |
| `PUBSUB_SUBSCRIPTION` | Subscription name or full resource path | required |
| `BQ_DATASET` | Curated dataset | `verdatrace_data_engineering` |
| `BQ_TABLE` | Curated table | `processed_events` |
| `RAW_ARCHIVE_BUCKET` | Controlled raw evidence archive | disabled when empty |
| `PSEUDONYM_SECRET_NAME` | Secret Manager secret ID | `verdatrace-pseudonym-salt` |
| `PSEUDONYM_SALT` | Direct local override | unset in cloud |
| `LOG_LEVEL` | Worker logging level | `INFO` |

## Security and governance

- The worker can subscribe only to its subscription, edit only its BigQuery dataset, create objects only in its archive bucket, and read only its pseudonym salt.
- GKE node and workload identities are separate.
- Raw storage has uniform access, public-access prevention, CMEK, and lifecycle deletion.
- User paths must stay within configured roots. External retrieval requires HTTPS and an exact host allow-list; redirects are not followed.
- Viewers cannot ingest or analyze. Ingestors cannot execute analytics. Steward/admin actions are explicit.
- Audit details redact secret-, token-, password-, credential-, API-key-, and raw-data-like keys.
- Direct identifiers are salted and hashed; the cloud worker refuses an empty salt.

See [docs/security.md](docs/security.md).

## Raster and remote-sensing foundation

`verdatrace.raster` defines one adapter boundary for GeoTIFF, COG, NetCDF, and Zarr profiles, metadata quality, chunked per-band statistics, duplicate scene IDs, and raster visualization recommendations. The built-in GeoTIFF adapter validates only the TIFF header and reports unknown pixel metadata; COG, NetCDF, and Zarr execution fail explicitly until a vetted rasterio/GDAL/xarray worker is installed. The Sentinel-2, ERA5-Land, and GHSL definitions in `config/datasets/` are disabled retrieval plans with official source links and no fabricated measurements. See [docs/raster.md](docs/raster.md).

## Compatibility and migration

`transform_event` remains import-compatible and existing canonical fields are preserved. Multimodal BigQuery columns are nullable additions. Existing consumers can continue selecting the original fields.

The previous repository head contained duplicate Terraform attributes, duplicate Kubernetes objects, malformed JSON fixtures, duplicated HTML, and an unparsable Python worker. Those files were normalized to the VerdaTrace resource names before adding features. Read [docs/migration.md](docs/migration.md) before applying Terraform to a project with existing resources.

## Performance boundaries

- CSV and NDJSON ingestion is iterative and supports bounded record counts and batching.
- The Pub/Sub worker processes individual events and BigQuery is partitioned by ingestion time and clustered by dataset, use case, and device.
- The portal renders only bounded generated samples; production UIs should request server-side spatial/temporal aggregates and vector tiles.
- GeoJSON JSON documents are currently materialized for standards-compliant parsing. Large vector sources should be converted to partitioned GeoParquet/BigQuery GIS outside the browser.
- Full raster processing requires a separate GDAL/rasterio-enabled worker and object-storage tiling strategy.
- Registered execution currently materializes each bounded file and embeds its records in the static payload. Large or streaming datasets require an adapter with pagination/query pushdown and a server-backed or pre-aggregated frontend contract.
