# Cohesive Data Pack integration

The supplied `VerdaTrace_Cohesive_Data_Pack.zip` is a synthetic, cross-linked
fixture. Its README and metadata are pack documentation; they are not runtime
instructions. The raw files are intentionally not committed because the pack is
about 95 MB and contains generated records. The repository commits the pack
README, manifest, schemas, catalog, quality rules, golden findings, lineage, and
RBAC metadata under `data/cohesive_pack/`.

## Reproduce the run

Extract the ZIP, then point the builder at the directory containing `raw/` and
`metadata/`:

```powershell
python scripts/build_demo.py `
  --pack-root C:\path\to\verdatrace_data_pack `
  --preview-limit 300
```

The same path can be supplied as `VERDATARACE_PACK_ROOT`. The generated static
payload contains bounded record previews and full-data aggregates; it does not
pretend that browser records are the full source.

## Layered flow

```text
raw pack files
  -> bounded CSV/JSONL/XML/GeoJSON ingestion
  -> configured quality findings and explainable dimension scores
  -> semantic profiles and catalog evidence
  -> Zone 360 / Site 360 / Vehicle 360 / Sensor Health rollups
  -> suitability and recommendation explanations
  -> visualization recommendations
  -> lineage, governance, RBAC, and audit summary
```

The existing Cairo Historical Weather and Synthetic Refrigerated Route datasets
still run through the original registry pipeline. Pack datasets are appended to
the same `datasets` payload array and use the same workspace renderer.

## Provenance and licensing

The pack identifies itself as generated by a synthetic generator. No external
provider URL or redistribution license is supplied, so manifests use the
explicit values `VerdaTrace Cohesive Data Pack (synthetic)` and
`not_provided`; they do not invent a license or measurements. Per-file SHA-256,
size, format, record count, ingestion timestamp, fixture flag, and source file
are recorded in the generated manifest/outcome.

## Quality validation

`quality_rules.csv` drives deterministic checks for logistics, mobility, IoT,
industrial, climate, and spatial data. `expected_quality_findings.csv` is
compared to detected counts in a machine-readable table containing expected
count, detected count, difference, and validation status. Exact targets must
match; approximate (`~`) targets are reported with a documented 25%/10-record
tolerance and remain visible for review.

The quality score is the arithmetic mean of eight explainable dimensions:
completeness, validity, uniqueness, consistency, referential integrity,
geometry quality, sensor quality, and freshness. Each dimension is
`max(0, 100 * (1 - issue_occurrences / records))`; no frontend score is
hard-coded.

## Cross-domain formulas

Environmental risk is computed per zone as:

`0.50 PM2.5 + 0.20 extreme-temperature + 0.20 precipitation + 0.10 low-visibility`

Zone suitability combines measured mobility, logistics, infrastructure,
environment, quality, and GIS coverage with weights 30%, 20%, 20%, 15%, 10%,
and 5%, then subtracts the measured environmental/GIS risk penalty. Zones at
least 70 are `recommended`, 50–69.99 are `review`, and lower scores are
`avoid`. Each decision exposes positive drivers, negative drivers, evidence
counts, and its quality impact.

The supplied `analytical_evaluation.csv` is retained as a validation target,
not copied into the recommendation logic. The payload reports its record count,
recommendation distribution, and zone-level mean absolute error against the
independently derived Zone 360 score under `platform.evaluation_alignment`.

The spatial foundation exposes WGS84 point-in-polygon and haversine proximity
helpers without forcing a heavyweight GIS dependency. Pack rollups primarily
use the supplied `zone_id` relationships; production-scale polygon joins
should move to a spatially indexed warehouse/vector-tile worker.

## Scaling boundary

JSONL and XML records are streamed. Master/reference files are small and are
indexed in memory; the browser receives at most the requested preview per
dataset. GeoJSON is parsed as one standards-compliant document, and the static
payload stores rollups rather than all raw features. A production deployment
should persist bronze/silver snapshots and serve server-side aggregates or
vector tiles for larger sources.
